## 1. Overview

FusionOS uses **PostgreSQL** as the primary transactional database and **Prisma** as the ORM. The database is the single source of truth for all business data.

**Core Principles:**
- Normalized relational modeling (no JSON blobs for business data)
- UUID primary keys on all entities
- Mandatory `tenantId` on all tenant-sensitive tables
- Integer minor units for monetary amounts (never floats)
- Proper foreign keys with explicit delete behavior
- Indexes on tenant-scoped hot paths
- Soft deletion only where legally/financially appropriate
- Timestamps on all entities

## 2. Multi-Tenancy Strategy

### Architecture

```
Shared PostgreSQL Schema
  + mandatory tenantId column on every tenant-sensitive table
  + server-side enforcement via Prisma extensions/guards
  + PostgreSQL RLS as defense-in-depth (Phase 4)
```

### Rules

1. **Every tenant-sensitive entity has a `tenantId` column** — no exceptions
2. **Server-side enforcement** — all queries pass through tenant-scoped Prisma extensions
3. **Frontend filtering is cosmetic only** — never a security boundary
4. **Cross-tenant access is a critical bug** — tested adversarially in Phase 4

### Tenant-Sensitive Tables

| Table | Has tenantId | Notes |
|---|---|---|
| Tenant | N/A | IS the tenant |
| Company | ✅ | Tenant owns companies |
| Branch | ✅ | Via company |
| Department | ✅ | Via company |
| Team | ✅ | Via company |
| User | ❌ | Users are platform-level, belong to tenants via UserRole |
| Role | ✅ | null = system-level role |
| Permission | ❌ | Platform-level, shared across tenants |
| UserRole | ✅ | Links user to role within a tenant |
| Employee | ✅ | Central business entity |
| EmployeeHistory | ✅ | Via employee |
| Designation | ✅ | Via company |
| EventOutbox | ✅ | Events are tenant-scoped |

## 3. Entity Boundaries

### Platform Kernel
- **Tenant** — isolated business entity on the platform
- **Company** — primary organizational unit within a tenant
- **Branch** — physical location/office
- **Department** — functional unit (hierarchical)
- **Team** — small group within a department

### Identity
- **User** — platform-level identity (can belong to multiple tenants)
- **Role** — set of permissions (system-level or tenant-scoped)
- **Permission** — granular access right (platform-level)
- **RolePermission** — many-to-many join
- **UserRole** — user-role assignment within a tenant (with optional scope)

### Employee
- **Employee** — central business entity (THE spine of FusionOS)
- **EmployeeHistory** — append-only employment change log
- **Designation** — job title/position

### Infrastructure
- **EventOutbox** — durable event persistence for transactional publishing

## 4. Identifier Strategy

| Strategy | Use Case |
|---|---|
| UUID v4 | All primary keys (generated by application/database) |
| Business code | Tenant-scoped identifiers (employee codes, dept codes) |
| No sequential IDs | External-facing IDs never use auto-increment |

**Rationale:** UUIDs prevent enumeration attacks, support distributed generation, and avoid exposing record counts.

---

## 5. Money Strategy

**Rule: NEVER use floating-point for financial data.**

| Concept | Implementation |
|---|---|
| Amount | INTEGER minor units (e.g., cents/pence/fils) |
| Currency | ISO 4217 3-letter code (e.g., "AED", "USD") |
| Example | AED 1,250.50 → amount: `125050`, currency: `"AED"` |

**Current usage:**
- `Employee.basicSalary` — integer minor units + `Employee.currency`

**Future usage (Phase 9+):**
- Payroll components, invoice amounts, payment amounts, journal lines — all integer minor units

---

## 6. Timestamp Strategy

| Field | Purpose | Required |
|---|---|---|
| `createdAt` | When the record was created | Always |
| `updatedAt` | When the record was last modified | Always |
| `deletedAt` | Soft deletion timestamp | Only where appropriate |

**Soft deletion is applied to:**
- Employee — employment records have legal significance

**Soft deletion is NOT applied to:**
- Audit logs — append-only, immutable
- Financial records — immutable
- EventOutbox — dispatcher handles lifecycle
- Users — status-based (ACTIVE/INACTIVE/LOCKED)

## 7. Indexing Strategy

### Principles
1. Every `tenantId` column is indexed (tenant-scoped queries are the hot path)
2. Composite indexes for common query patterns
3. Foreign key columns indexed for join performance
4. Unique constraints enforce business rules at DB level

### Important Indexes

| Table | Index | Purpose |
|---|---|---|
| Company | `(tenantId, code)` | Tenant-scoped code lookup |
| Branch | `(companyId, code)` | Company-scoped code lookup |
| Department | `(companyId, code)` | Company-scoped code lookup |
| Department | `(branchId)` | Branch-scoped queries |
| Team | `(departmentId, code)` | Department-scoped code lookup |
| User | `(email)` | Login lookup |
| Role | `(tenantId, name)` | Tenant-scoped role lookup |
| UserRole | `(userId)` | User's roles |
| UserRole | `(tenantId)` | Tenant's user-role assignments |
| Employee | `(tenantId, employeeCode)` | Tenant-scoped employee lookup |
| Employee | `(tenantId, email)` | Tenant-scoped email lookup |
| Employee | `(tenantId, employmentStatus)` | Status-filtered queries |
| Employee | `(departmentId)` | Department-scoped queries |
| Employee | `(managerId)` | Reporting hierarchy |
| EmployeeHistory | `(employeeId, effectiveDate)` | Chronological history |
| EventOutbox | `(status, createdAt)` | Polling pending events |

## 8. Constraint Strategy

### Unique Constraints

| Table | Columns | Business Rule |
|---|---|---|
| Tenant | `slug` | Globally unique tenant slug |
| Company | `(tenantId, code)` | Tenant-scoped company code |
| Branch | `(companyId, code)` | Company-scoped branch code |
| Department | `(companyId, code)` | Company-scoped department code |
| Team | `(departmentId, code)` | Department-scoped team code |
| User | `email` | Globally unique email |
| Role | `(tenantId, name)` | Tenant-scoped role name |
| Permission | `name` | Globally unique permission name |
| UserRole | `(userId, roleId, tenantId)` | One role per user per tenant |
| RolePermission | `(roleId, permissionId)` | No duplicate assignments |
| Employee | `(tenantId, employeeCode)` | Tenant-scoped employee code |
| Employee | `(tenantId, email)` | Tenant-scoped employee email |
| Designation | `(companyId, code)` | Company-scoped designation code |

### Foreign Key Behavior

| Relation | Delete Behavior | Rationale |
|---|---|---|
| Tenant → Company | Cascade | Tenant deletion removes all data |
| Company → Branch | Cascade | Company deletion removes branches |
| Company → Department | Cascade | Company deletion removes departments |
| Branch → Department | SetNull | Department survives branch deletion |
| Department → Team | Cascade | Department deletion removes teams |
| Department → Department (parent) | SetNull | Orphaned dept becomes root |
| Employee → Company | Cascade | Company deletion removes employees |
| Employee → Branch | SetNull | Employee survives branch deletion |
| Employee → Department | SetNull | Employee survives dept changes |
| Employee → Team | SetNull | Employee survives team changes |
| Employee → Designation | SetNull | Employee survives designation deletion |
| Employee → Employee (manager) | SetNull | Manager deletion doesn't cascade |
| User → Employee | SetNull | User deletion doesn't remove employee record |
| UserRole → User | Cascade | User deletion removes role assignments |
| UserRole → Role | Cascade | Role deletion removes assignments |
| UserRole → Tenant | Cascade | Tenant deletion removes assignments |
| RolePermission → Role | Cascade | Role deletion removes permission mappings |
| RolePermission → Permission | Cascade | Permission deletion removes mappings |

## 9. Soft Deletion Strategy

**Where soft deletion IS used:**
- `Employee` — employment records have legal and financial significance. Never hard-delete.

**Where soft deletion is NOT used:**
- Audit logs — append-only, immutable by design
- Financial records — immutable, never deleted
- EventOutbox — managed by dispatcher lifecycle
- Users — status-based deactivation (ACTIVE/INACTIVE/LOCKED)
- Organizational entities — hard-deleted with cascade where business-appropriate

## 12. Event Outbox Strategy

The `EventOutbox` table provides durable persistence for domain events.

**Flow (Phase 17):**
```
Business Transaction
  → Write business data
  → Write event to outbox (same transaction)
  → Commit
  → Dispatcher polls PENDING events
  → Dispatches to consumers
  → Marks as DISPATCHED
```

**Current status:** Table exists. Dispatcher implementation is Phase 17.
